# PROBE: the AI's level-halting-boss approach term is LIVE, and CALIBRATED
#
# PINS:   cards f4d1721f -> 31ceb6ff -> b56633fb. The term expresses "close on that boss" by
#         writing `steerTarget`, and it has failed twice in two different ways. First it was
#         PARKED: every steerTarget vote weighed SeekWeight 0.8 against a whole-sum 0.95 "park",
#         so DoAIMove's last act zeroed it and the ship never went (card 31ceb6ff gave it its own
#         weight, card ada9e839 deleted the park). Then it was MIS-CALIBRATED: that weight, 1.1,
#         was only ever chosen to clear the park, and the boss's own repellent at the point the
#         ship was being sent is 2.9 -- so the net force pointed AWAY from its own destination and
#         `bossfar` read ~99% forever. Card b56633fb solves the weight against that repellent at
#         firing range instead (PlayerShip.BossApproachWeight).
#
# WHY A PROBE AND NOT A SCREENSHOT: the failure is a ship that does not GO somewhere, on a rig
# where a dozen other terms are also pushing, so a frame shows nothing and `deaths`/`prog` move
# for unrelated reasons. `AiBench.NoteBossApproach` counts it where the term acts and the run
# prints `boss=<mean edge px> bossfar=<pct> bossw=<mean solved weight>`.
#
# THIS PROBE NOW ASSERTS A NUMBER, and picking WHICH number needed the mutation run rather than
# an argument. It was deliberately weak before (`bossfar=[0-9]+%`, i.e. "the counter exists")
# because the parked and un-parked builds both read ~99% and nothing here separated them.
#
# `bossfar` alone would still not do it, and the reason is a trap worth stating: the pre-card
# ~99% was measured against the pre-card REFERENCE, the 41px-edge standoff radius. Card b56633fb
# re-references it to r* -- firing range, 118px edge on this rig -- which is much farther out, so
# the SAME steering scores far better on the new metric. Measured over seeds 1-3, pre-card
# standoff+1.1 reads 49/60/52% here, not 99%.
#
# So the discriminating leg is `idle%` -- ticks with a shootable target and no shot fired, i.e.
# whether the bot is actually in range to FIGHT the boss, which is what closing was ever for.
# Measured, Very_Hard / ?invuln / 180 sim-s / seeds 1-3: this build 15/10/11%, pre-card standoff
# 31/41/32%. The 25% threshold sits 1.7x above the worst passing run and 1.24x below the best
# failing one. `bossfar` keeps a leg too, at 45% (36% worst pass / 49% best fail), because the two
# fail in different ways -- a bot held out of range and a bot in range that has stopped shooting.
#
# `boss=` IS AN EDGE DISTANCE since that card, not a centre distance, so the same rig reads
# ~130-165px where it used to read ~390. Do not compare the two across the card.
#
# `bossw=` is the SOLVED weight, averaged over the ticks the term ran. Under the lap-12 baked
# curve (p=4) it reads ~0.01 here BY DESIGN -- the solve equals the boss's own repellent at
# firing range, and the spike curve is nearly zero at r*'s 118px -- so the old non-zero leg
# (pre-curve-flip it read 0.7-1.2) was RETIRED: near-zero is the honest calibration now, and an
# inert term is what the idle%/bossfar legs discriminate. Only presence is asserted.
#
# FAILURE MEANS:
#   * `boss=` / `bossfar=` missing  -> NoteBossApproach is no longer called, i.e. the haltingBoss
#                                      branch of DoAIMove was removed or its predicate
#                                      (IsAiPriorityTarget) stopped matching BrainBoss. The term
#                                      is gone, not merely mistuned.
#   * `bossfar` back near 99%       -> the term runs but is out-voted at its own destination --
#                                      the card b56633fb defect, or a repellent that has grown.
#                                      Read `bossw=` next: near-zero means the solve went inert,
#                                      a healthy weight means something else is winning.
#   * `boss=0px`                    -> the branch runs but the boss is never on screen; the
#                                      ?brainboss fast-boot changed, not the AI.
#   * `pickups=` missing            -> AiBench's counters were reshaped; see card ada9e839.
#
# MUTATION-TESTED: restoring the pre-card standoff+1.1 verbatim (the geometric standoff point
# carrying DefaultSeekApproachWeight) turns the idle and bossfar legs red while every other line
# still passes -- which is the mutation the previous revision of this probe could NOT catch, and
# said so. Deleting the AiBench.NoteBossApproach call drops the boss fields and turns four legs
# red. NOTE the first mutation passed an 80% bossfar threshold, which is how the numbers above
# came to be measured rather than reasoned: re-mutate before loosening either bound.
#
# eahl: --flags "?level=Level3&brainboss&aiplayer&aibench&difficulty=Very_Hard&invuln&seed=1"

step 150 nodraw
mark

# 180 sim-seconds of real bot against the boss.
eval AiBenchRun 60
eval AiBenchRun 60
eval AiBenchRun 60

eval AiBench

# The run got where it claims: a live level, the bot steering, the boss seen.
expect \[aibench\].*Level3
expect \[aibench\].*ticks=[1-9][0-9][0-9][0-9]
expect \[aibench\].*boss=[1-9][0-9]+px

# CALIBRATED, the discriminating leg: the bot is in range to FIGHT the boss, so it is not sitting
# on a shootable target doing nothing. Under 25% -- see the header for how that bound was measured.
expect \[aibench\].*idle=([0-9]|1[0-9]|2[0-4])%

# ...and it got there by closing: under 45% of ticks outside firing range.
expect \[aibench\].*bossfar=([0-9]|[1-3][0-9]|4[0-4])%

# The solved weight is reported (near-zero is the honest p=4 calibration -- see the header).
expect \[aibench\].*bossw=[0-9]+\.[0-9]+

# The powerup counters ride the same report (card ada9e839) -- if they vanish, the histogram
# reshaped and the matrix runner's Row() contract is the next thing to check.
expect \[aibench\].*pickups=[0-9]+/[0-9]+\([0-9]+%\)

quit
