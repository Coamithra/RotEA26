# PROBE: the clickable "(B) back" tip never overlaps a menu entry's hit box
#
# PINS:   card 2a4110d0. The bottom-left back tip is clickable, but it is NOT a menu entry --
#         it is scene chrome (MenuScene.drawButtonTips) with its own box in Compat/BackTipHit,
#         while the entries record theirs via MenuSub1.RecordEntryHit. If the two boxes ever
#         overlap, ONE click both goes back AND activates the row it landed on.
#         Nothing enforces that; it holds only because two unrelated layouts happen to leave a
#         gap (tip x<=146, the widest main-menu frame starts at x~218). Widen a frame, lengthen
#         a label, or move General.SafeZone and it stops holding -- with no build error, no
#         crash and no visible symptom until a player clicks "back" and launches a mission.
#
#         So MenuSub1 prints its own verdict on each layout change and this asserts it, across
#         the three menu layouts that differ: the framed main menu (widest frames, and the one
#         that shifts up at 8 unlocked rows -- card 45c16ef6), the plain centred list, and a
#         carousel (whose boxes are 800x600*scale screenshots, by far the biggest here).
#
# FAILURE MEANS: read the quoted line's `overlap=<n>` -- n is the entry index the tip now
#         collides with. Either the tip grew (a longer label, a bigger icon, a moved safe zone)
#         or that menu's boxes did. Do not "fix" it by shrinking the assertion; the click really
#         does double-fire in that state.
#
# The POSITIVE assertions are structural, not decoration: `expect-not` alone would pass on a
# run that never opened a menu at all, which is the failure mode this file is most likely to
# rot into. Mutation-tested by widening the recorded tip box by 200px -- the main menu then
# reports `overlap=7` (Exit) and this goes red on both the expect-not and the main-menu expect.
#
# ---------------------------------------------------------------------------------------------
# WHY THIS FILE ALSO ASSERTS THE MOUSE (card 83054936)
#
# This probe used to fail 15 of 20 runs, on a leg that VARIED between runs, and it was not the
# tip maths -- it was the DEVELOPER'S DESKTOP MOUSE. KNI's SDL2 backend answers Mouse.GetState()
# from SDL_GetGlobalMouseState (decompiled from Kni.Platform.dll), a global focus-INDEPENDENT
# read of the pointer and the button mask minus the hidden window's origin, so an eahl run
# sampled whatever the human's hand was doing. MenuSub1.HandleMouse then hover-selected whatever
# entry the cursor moved over AND returned true, which makes HandleInput return early and swallow
# that tick's keypress -- so `down`+`enter` from Start once launched the TUTORIAL. A physically
# HELD left button separately ate section 2's scripted click, because pressedAndIdle[Mouse1] was
# already true when the rising edge was scripted.
#
# eahl now declares that there is no physical mouse (HeadlessHost.Boot ->
# DebugInput.SuppressPhysicalMouse), which fixes it for every probe at once rather than sprinkling
# `eval MouseAt` into the nine that navigate menus. The two lines below are the POSITIVE assertion
# of that guard -- it changes no pixel, so nothing else can see it, and a probe suite that merely
# runs green proves nothing about a guard it never looks at.
#
# MUTATION: run this probe with `--real-mouse`. `physical=live` and a `pos=` reading off the real
# desktop pointer make both lines go red, deterministically -- which is exactly why that flag
# exists.
# ---------------------------------------------------------------------------------------------
#
# eahl: --flags "?menu&unlockall&noattract"

# mark FIRST, then settle: the report prints only when a menu's layout CHANGES, so the main
# menu's line lands during boot -- a mark placed after the settle would scope the window past
# the very line it is here to assert. The boot noise this normally guards against is other
# cards' `(boot)` decode lines, which none of these patterns can match.
mark

# Settle past the boot white fade.
step 200

# THE RIG'S OWN PRECONDITION, asserted before anything depends on it (probes README rule 5): the
# keyboard navigation below is only repeatable because no physical cursor can steal the selection.
# `pos=` is the consequence, `physical=` is the cause -- assert both, since a suppression flag
# that stopped being READ would leave the first line green.
eval MouseState
expect      \[mousestate\] physical=suppressed override=none pos=-1000,-1000

# --- the framed main menu, all 8 rows unlocked (the 45c16ef6 shifted layout) ---
# The tip GEOMETRY is pinned exactly, not wildcarded, because section 2 clicks a hard-coded
# point inside it: wildcard this and moving the tip leaves section 1 green while section 2 fails
# as "the back tip is broken", which is the wrong diagnosis at the wrong line.
expect      \[backtip\] menu=MenuSubWithSkull entries=8 tip=40,534,106,36 overlap=none

# --- a plain centred list (Options) ---
eval Press down 1
step 5
eval Press enter 1
step 150
expect      \[backtip\] menu=MenuSub1 entries=\d+ .* overlap=none

# Back out to the main menu. The selection is left on Options, so step back UP to Start --
# without this, `enter` re-opens Options and the carousel assertion below never gets there.
eval Press escape 1
step 120
eval Press up 1
step 5

# --- a carousel, whose entry boxes are the largest in the game ---
eval Press enter 1
step 200
expect      \[backtip\] menu=SubMenuLevelChoice entries=\d+ .* overlap=none

# THE GEOMETRY ASSERTION: nothing reported an overlap anywhere in that walk.
expect-not  \[backtip\] .* overlap=[0-9]

# Back to the main menu for section 2.
eval Press escape 1
step 150

# =====================================================================================
# SECTION 2 -- the tip actually GOES BACK when clicked (PR #255 follow-up)
#
# Reachable here only because `eaMouseAt` parks the cursor in DESIGN space: `eaPress` supplies
# the button, but every mouse consumer is position-dependent and the position used to come only
# from Mouse.GetState(), which no script can move. Before that seam this leg needed real Chrome.
#
# `eaMenuCensus` is the observable -- which menu is LIVE. The [backtip] line cannot serve here:
# it prints only when a layout CHANGES, so returning to a menu already seen prints nothing.
# =====================================================================================
mark

eval Press down 1
step 5
eval Press enter 1
step 150
# Precondition, asserted rather than assumed: we really are in the submenu. Without this the
# "back on the main menu" check below passes on a run that never left it.
eval MenuCensus
expect      \[menucensus\] count=1 live=MenuSub1

# NEGATIVE CONTROL: same click, cursor somewhere with no entry and no tip. If this moved us,
# the assertion below would be about clicking anywhere rather than about the tip.
mark
eval MouseAt 700 100
step 2
eval Press Mouse1 1
step 120
eval MenuCensus
expect      \[menucensus\] count=1 live=MenuSub1
expect-not  \[menucensus\] count=1 live=MenuSubWithSkull

# THE CLICK. Cursor inside the tip box pinned in section 1 (40,534 .. 146,570).
mark
eval MouseAt 93 552
step 2
eval Press Mouse1 1
step 120
eval MenuCensus
expect      \[menucensus\] count=1 live=MenuSubWithSkull

# The release path, which nothing else here covers: MouseClear must report what it let go of.
# (The override is a process-lifetime static and this is the last line, so the release itself
# protects nothing -- asserting its line is what gives the method any coverage at all.)
mark
eval MouseClear
expect      \[debug\] eaMouseClear .* \(was 93,552\)

quit
