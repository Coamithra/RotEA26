# PROBE: the enemy laser-charge glow's AIM on a join peer.
#
# PINS: card eb057163 -- Compat/Net/NetChargeAimTest, driven by eaNetChargeAim() / `eval
# NetChargeAim`.
#
# THE REPORT was "the twin motherships in level 2 do not change where they are aiming visually as
# their target moves while they charge their laser", seen on P2. TWO mechanisms produce that
# sentence and they need OPPOSITE fixes, so section 1 exists to tell them apart before anything is
# changed -- a FREEZE (the client's aim is written once and never again, so something in the
# encode/apply/drive chain latches) or STALENESS (the aim is re-applied correctly, but only on that
# boss's round-robin snapshot turn, so it is a staircase).
#
# WHAT IT MEASURED, and the number is asserted below so it cannot quietly change: STALENESS. Over
# one full 2500ms windup at a representative 150ms turn, the pre-card client moved its aim on
# **15 of 144 ticks**, in **7.62px** jumps. Not a freeze -- every one of the 16 aims the host sent
# arrived and was applied. So the fix is client-side and needs NO wire change.
#
# THE FIX is an EASE, not the extrapolation the card's own analysis proposed. The glow now sweeps
# toward each newly replicated aim over NetPuppets' own cadence-derived correction window
# (max(150ms, 2 x SnapshotTurnMs) -- the same window the position error drains over, because the
# aim arrives on the same turn and so has the same staleness). Extrapolating an angular RATE was
# considered and declined: an aim is a CHASE, so its rate reverses whenever the player does, and an
# extrapolated glow would point somewhere the host never aimed and then snap when the real beam
# fires along the host's true angle. A telegraph that LIES is worse than one that lags, and the
# repo's grain runs away from difference-estimators (cards e79bb994, c1a38ef9).
#
# THE DRAIN SHAPE IS NetPuppets.Drive'S, VERBATIM -- a fraction of what remains OF THE WINDOW, so
# it lands exactly on the target on the window's last tick and is FRAME-RATE INDEPENDENT. The
# obvious one-liner (a fraction of the whole window each tick) is an exponential decay that never
# lands and whose speed depends on the frame rate -- i.e. precisely the drain CorrectionWindowFor's
# own header records as measured and REJECTED. It shipped that way in the first cut and review
# caught it; section 6 is what would have caught it, and is why section 6 exists.
#
# FAILURE MEANS: read the quoted PASS/FAIL line. NOTHING here throws and NO counter moves -- the
# glow is draw-only, so both the defect and the fix are invisible to every metric the game already
# produces, and a STEPPING aim and a SWEEPING aim are the same still frame. Data is the only
# evidence there is.
#
# THE NEGATIVE CONTROL IS A SHIPPED FLAG, `?netaimease=0` (in DebugFlags.Active, the
# ?netstaleguard=0 deliberate-bug-repro idiom). The suite drives it through the injected INetHost
# rather than by rebooting, so sections 1 and 2 are literally the same frames with the fix off and
# on -- one session, one puppet, no confound. Without section 1, "the fixed aim sweeps smoothly"
# would pass on a build where the aim never moved at all, which is one of the two faults under test.
#
# MUTATION-TESTED SIX WAYS, each isolated, five of them failing DISJOINT legs:
#   * the ease removed entirely (i.e. pre-card)      4 FAIL (all three s2 comparisons + the s6
#                                                            zero-tick hold)
#   * the charge-on edge's recycle reset dropped     5 FAIL (s1 aim count, s4, both s5 legs, s6)
#                                                           -- note it fails the FIXED-offset
#                                                           emitter too, i.e. the pooled-emitter
#                                                           trap does real damage on a type whose
#                                                           aim never moves at all
#   * an EXPONENTIAL drain (fraction of the whole     2 FAIL (both s6 dt legs, and NOTHING else --
#     window per tick, the first cut)                        which is exactly why s6 exists)
#   * the ?netaimease=0 flag made inert              4 FAIL (s1's staircase verdict + s2's controls)
#   * a zero-length tick read as "window over"       1 FAIL (the s6 zero-tick hold)
#   * the window LATCH dropped (re-read live)        0 FAIL -- see below
#
# THE WINDOW LATCH IS A REVIEW INVARIANT HERE, NOT A PROBED ONE, and that is stated rather than
# papered over: the rig holds ONE puppet, so `CorrectionWindowMsNow` is constant throughout and
# re-reading it mid-drain is indistinguishable from latching it. It matters in play (a spawn burst
# mid-drain would otherwise rescale the fraction already applied), and covering it would mean
# driving the live puppet population up and down mid-sweep for one assertion.
#
# NOTE section 4's no-op is ALGEBRAIC and no test can discriminate a good ease from a bad one
# there: with target == current, `Offset += (Target - Offset) * f` is identically Offset for any f.
# What it catches -- and did catch under mutation -- is the charge-on RESET going missing. The
# section says so; do not re-read it as "the ease was measured not to wobble".
#
# NOTE the pinned EASED numbers (135/144 ticks, 0.85px) are a function of
# `NetPuppets.CorrectionWindowMs` (150) and the suite's own 16.7ms tick. A legitimate retune of
# that SHARED constant will fail those two lines for a reason that has nothing to do with the aim
# -- re-derive them rather than assuming a regression. The pre-card pair (15/144, 7.62px) is
# policy-free and is the one that pins the defect.
#
# MENU-ONLY and leave-no-trace (verified by running the suite TWICE in one process -- identical
# tallies). It starts a REAL (in-process, wire-backed) client session and builds real puppets into
# the live bin, so it SKIPs itself over a live session, level or attract demo -- `?noattract` is
# not decoration, without it the idle demo makes every leg skip. It is NOT silent: the charge glow
# is deliberately audible on a join peer (cards 57ea30cd / c146422f), so a run plays the looped
# `lazercharge` cue several times.
#
# GOTCHA the suite now asserts against, because it was silently true for three whole sections:
# while a CLIENT session is up, `NetSession.SuppressWorldSpawn` DIVERTS any replicable-type
# `ComponentBin.Add` into the recycle pool. A section that plants a real enemy must therefore stop
# the session first AND check the plant landed, or it tests an entity the world never held.
#
# DELIBERATELY ABSENT FROM net_selftests.txt despite being menu-runnable -- it has its own probe,
# which carries this card's write-up and mutation matrix, so listing it in both would run it twice
# for nothing. The eaNetDeathFx / eaNetStale precedent.
#
# eahl: --flags "?menu&noattract"

step 200 nodraw
mark
eval NetChargeAim

expect \[netaim\] enemy charge-glow AIM on a join peer
expect 1\. the mechanism: FREEZE or STALENESS, measured
expect 2\. the EASE -- the same frames, swept instead of stepped
expect 3\. the HOST re-reads its live aim every encode
expect 4\. an emitter whose offset does NOT track is left alone
expect 5\. the charge-off edge, and the recycle trap behind it
expect 6\. the dt the driver really hands it

# THE VERDICT ITSELF, as printed rather than only as a PASS line -- if the mechanism ever changes
# shape (a freeze creeping in, or the pre-card path somehow sweeping) this is what says so.
expect pre-card  verdict=STALENESS \(staircase\)
expect eased     verdict=SWEEPING
# The defect as a NUMBER, at the conditions the card quotes it at. A build that stopped stepping
# with the flag off would make every section-2 comparison vacuous.
expect pre-card .* moved on 15/144 ticks  maxStep=7\.62px
# ...and the fix as one. Read these together: the same 16 aims and the same ~105px of travel,
# spread over 135 ticks in sub-pixel steps instead of 15 ticks in 7.62px ones.
expect eased .* moved on 135/144 ticks  maxStep=0\.85px

# The SKIP guard: a run that skipped prints no tally, so this is what tells "the menu was busy"
# from "the suite passed".
expect-not SKIP \(run from the main menu
# A TALLY, never `expect-not FAIL` on its own: an absence assertion passes on a run where the eval
# never happened at all. Raise it when legs are added; never lower it to make a run green.
expect \[netaim\] 28 passed, 0 failed
expect-not FAIL
quit
