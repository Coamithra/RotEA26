# PROBE: one tap of the fire button must reach the other peer as ONE bullet, not two.
#
# PINS: card a5c2a39b ("if P1 taps once to shoot a single bullet, P2 sees two bullets flying").
# The card guessed we replicate mousedown+location. We do not -- the wire carries firing STATE on
# MsgShipState and the peer re-fires through the real FireAt path. The defect was arithmetic:
# SendShipState streamed firing=true for a flat 150 ms while the peer re-fires through a cadence
# gate of 1000/shotsPerSec = 125 ms at the default 8 shots/sec, so one tap spawned
# 1 + floor(150/125) = 2 bullets over there (3 at the maxed 18/s). Those phantom bullets are real
# in the peer's world and damage what they hit, which is the card's other symptom -- "P1 can kill
# an enemy on P2's screen that is alive on P1's".
#
# WHAT IT ASSERTS (Compat/Net/NetFireTest.cs carries the full reasoning):
#   1. The contract as a PURE DECISION, over every reachable fire rate: the worst-case number of
#      packets a hold marks, times the send interval, must stay under one cadence period. The
#      pre-card flat 150 ms hold is computed beside it and must VIOLATE that, so a predicate
#      that had degenerated into "always true" cannot pass. Plus the other half of the trade --
#      every rate still marks at least one packet, so no tap goes unsent.
#   2. The symptom END TO END over a real NetWire: a scripted peer taps once, the real remote
#      puppet is driven at 60 Hz, and the bullets it spawns are COUNTED. Exactly 1.
#   3. The same at the maxed fire rate (18/s, a 55.6 ms period) -- where the fix has least room.
#   4. THE NEGATIVE CONTROL, and the reason a green run means anything: the identical rig is fed
#      the packet pattern the PRE-CARD sender produced for one tap and must still report TWO.
#      If leg 4 ever reports 1, the rig has stopped being able to see the bug.
#   5. The overcorrection guard: ~1 s of held fire must still produce the owner's cadence (8 at
#      8/s), not one bullet per packet (30) and not zero. Without it, "always 1 bullet" -- a
#      re-fire that had stopped working entirely -- would pass legs 2-4.
#
# MUTATION-TESTED TWO WAYS, and the second one is why leg 1 is not redundant:
#   * the pre-card flat 150 ms hold restored -> leg 1 fails (first violation at 7/s), leg 2
#     reports 2 and leg 3 reports 3. Leg 4 still passes, as an independent control should.
#   * a 0.6-fraction-of-the-period hold (this card's first attempt; 37.5 ms against the 62.5 ms
#     period at 16 shots/sec) -> leg 1 fails at 16/s and EVERY end-to-end leg passes. The rig
#     aligns packets to tick boundaries, so legs 2-5 sample one phase of the alignment and a
#     marginally-too-long hold can land on the safe side of it. Leg 1 is what covers the top of
#     the range; do not read a green leg 3 as doing so.
#
# DESTRUCTIVE, so it gets a process to itself (the runner gives every probe one anyway): it pairs
# a real host session onto the live level, seats a Remote puppet and fires real bullets into the
# world. Teardown stops the session, sweeps the bullets and frees the Remote seat, and asserts it
# did.
#
# ?level=Level2 for a level that just runs with one keyboard player and a live ship (the suite's
# rig precondition -- a partner-seating level would seat a second slot and it would report rather
# than assert), ?invuln so the settle cannot lose that ship, ?noattract because the suite needs
# the LEVEL and not a demo.
#
# eahl: --flags "?level=Level2&invuln&noattract"

step 400 nodraw
mark
eval NetFire

expect \[net\] session start role=host .* transport=InMemory
expect \[netfire\] single-tap bullet count
expect 1\. the hold-window contract over every reachable fire rate
expect 2\. rig -- a real HOST session, a scripted peer and its ship puppet
expect 3\. the same tap at the maxed fire rate
expect 4\. NEGATIVE -- the pre-card packet pattern
expect 5\. sustained fire still runs at the OWNER'S cadence
expect 6\. teardown
# The counts themselves, not just the leg headings -- a bullet count is the whole subject here,
# and "got 1" is the assertion the card is about. The negative control's "got 2" is asserted just
# as hard: a rig that stopped reproducing the bug would otherwise go quietly green.
expect spawns exactly ONE bullet on the peer \(got 1\)
expect spawns exactly ONE bullet \(got 1\)
expect spawns TWO bullets for one tap .* \(got 2\)
# A TALLY, never a bare `expect-not FAIL`: an absence assertion passes on a run where the eval
# never happened, and this suite skips its end-to-end legs on a bad precondition. Raise the count
# when checks are added.
expect \[netfire\] 16 passed, 0 failed
expect-not FAIL
expect-not SKIP
quit
