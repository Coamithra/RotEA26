# PROBE: every reposition site in real play is MARKED, and the diagnostic that would catch a
# missed one still clears every genuine mover.
#
# eahl: --flags "?level=Level2&invuln&aiplayer&difficulty=Inzane"
#
# PINS: the teleport marker (card e79bb994) and NetSession.MaxObservedSpeedPxPerMs.
# CaptureBaseState stamps each entity's wire velocity as a finite difference between its snapshot
# turns, which cannot tell motion from a REPOSITION -- the SpiderBoss is parked at the far screen
# edge to start each fly-by, and differentiating that ~800px jump put 42-57 px/ms on the wire. The
# client snapped to the new position (correct) and then DEAD-RECKONED onward at teleport speed,
# and since puppets are collidable it crossed the screen and killed the local player.
#
# WHAT CHANGED UNDER THIS PROBE, because its verdict now rests on a different mechanism.
# Card 8dabe812 fixed that with a plausibility CAP: any sample above 5.0 px/ms had its velocity
# refused. Card e79bb994 deleted the cap -- the host KNOWS when it teleports something, so the
# reposition sites call AlienDrawableGameComponent.NetNoteTeleport and the marker rides the wire
# as a per-sample flags byte. 5.0 survives only as a DIAGNOSTIC threshold: nothing above it reads
# the number any more, and NetSession.NoteIfUnmarkedTeleport just names a type on the console.
#
# SO THIS FILE ASSERTS TWO DIFFERENT THINGS, and the first one is new.
#
# 1. `expect-not UNMARKED teleport` -- COVERAGE. Every reposition reachable in this soak went out
#    marked. This is the leg the marker made possible and it is the important one: the marker is
#    only as good as its call sites, and a MISSED site fails exactly the way the original bug did
#    -- silently, on the other player's screen, one type at a time. No cap and no scan could
#    assert this; the cap simply swallowed a missed site, indistinguishably from a marked one.
#    MUTATION-TESTED: dropping the NetNoteTeleport() call from SpiderBoss.cs's fly-by re-park
#    fails this leg with `[net] UNMARKED teleport suspected: SpiderBoss at <n> px/ms`.
#
#    **THE `marked=` LEG IS WHAT KEEPS IT HONEST, and the first cut of this probe was VACUOUS
#    without it.** An absence assertion passes on a run that never reached the code, and there
#    are two ways to reach nothing here. (a) The detector: NetSession.CaptureBaseState's copy of
#    the diagnostic only runs inside a LIVE HOST SESSION, and this soak has none -- measured, a
#    30000-frame run produced not one line whether the markers were intact or deleted. That is
#    why the audit lives in eaNetVelScan, which needs no session. (b) The subject: a build with
#    every marker removed prints no UNMARKED lines from the scan EITHER -- it simply stops
#    announcing repositions. So the table's `marked=` count on a known repositioning type is the
#    positive control, and `expect SpiderBoss .* marked=[1-9]` is asserted below.
#
# 2. The [velscan] legs -- the diagnostic must not CRY WOLF. If the threshold sat below a real
#    fast mover, that type would print the UNMARKED line forever and the leg above would go red
#    on a build with nothing wrong with it. So the ceiling under the threshold still has to be
#    measured, which is what eaNetVelScan does. (The stake is lower than it was: as a cap, a
#    threshold set too low silently CLIPPED a fast enemy and recreated this whole family's
#    stutter. As a diagnostic the worst case is a spurious line.)
#
# HOW eaNetVelScan MEASURES IT (Compat/Net/NetVelocityScan.cs has the full reasoning): it samples
# every replicable entity's position at the 60ms snapshot cadence -- the same finite difference
# CaptureBaseState takes -- and reports each type's SUSTAINED speed, meaning one whose neighbouring
# sample is at least half as fast. A reposition is a one-interval spike by definition; flight holds
# its speed on at least one side. Types that reposition as part of ordinary play (EvilSkull
# respawns at a random point, a `wrapping` Braineroid teleports across the screen, a Ball wraps on
# all three edges, SpiderBoss parks for its fly-by) are named in that file and EXCLUDED from the
# verdict -- the scan cannot tell a jump from motion, which is precisely why the GAME now says so.
# **Never "fix" a FAIL by adding a type to that exclusion list alone**: that silences the verdict
# and leaves the actual bug in place. The type needs its NetNoteTeleport call, which is what leg 1
# is here to insist on.
#
# FAILURE MEANS: read the table on the [velscan] lines. A [velscan] FAIL names a type whose
# SUSTAINED speed is at or above the threshold -- either it is genuinely that fast, in which case
# RAISE NetSession.MaxObservedSpeedPxPerMs, or it repositions, in which case give it a
# NetNoteTeleport call AND a RepositioningTypes entry with the code line that proves it.
# An UNMARKED line means the named type repositions somewhere the marker was not added.
#
# WHY LEVEL 2 AT Inzane. The binding constraint in the whole game is MarsBoss's entry PowerCurve
# at 2.404 px/ms -- nothing else that genuinely moves comes close (Spider 1.237, PlasmaBall 0.600,
# EvilBullet 0.240, and the fastest DECLARED speed anywhere is EvilSkull's launched MaxSpeed 2.5).
# Level 1 and Level 3 were swept by hand at the same settings and top out at 0.240 and 0.600
# respectively, i.e. they have ~10x of slack and could not fail this before Level 2 did. Inzane
# because several speeds are difficulty-scaled and the threshold has to clear the worst case. It
# is also the level that carries the SpiderBoss, i.e. the reposition site the card is about, which
# is what makes leg 1 non-vacuous here. If a future card adds a fast type or a reposition site to
# another level, sweep it by hand with `eval NetVelScan` before assuming this probe covers it.
#
# `&invuln&aiplayer` so the run is unattended and cannot end early on a death, which would cut the
# soak short and under-report the ceiling.
#
# IF `expect MarsBoss` IS THE LEG THAT FAILS, THAT IS PROBABLY NOT A REGRESSION. It is a bet on
# an unseeded AI run reaching the boss inside 30000 frames, which is the one soft-real-time
# assertion in this file. Re-run it once before investigating: a genuine threshold regression fails
# the `-- PASS` leg with a [velscan] table present, whereas this one fails with the boss simply
# absent from the table. If it starts failing REPEATEDLY, the AI has stopped clearing Level 2
# rather than anything here having broken -- check the AI completion matrix, not this card.
#
# THE SOAK IS LONG ON PURPOSE (~8 sim-minutes). MarsBoss arrives deep into Level 2: a
# 5000-frame run never reaches it at all and reports UFO 0.758 as the fastest thing in the game,
# which is a PASS FOR THE WRONG REASON. That is why `expect MarsBoss` is here as the positive
# control -- without it this probe would go green on a run that measured nothing interesting, and
# leg 1 would go green on a run that reached no reposition either.
#
# THIS PROBE ALREADY EARNED ITS KEEP TWICE while card 8dabe812 was being written: a first cut at a
# 3.0 threshold FAILED here on MarsBoss (only 1.25x of headroom over its 2.404 peak), and before
# that the scan's own sampler was differencing across POOL RECYCLES and reported an EvilBullet
# whose declared Speed is 0.24 px/ms at a sustained 14.9. Neither would have been visible in a
# frame. Card e79bb994's own audit then found a FOURTH repositioning type this scan had never
# named -- Ball, whose screen wrap the old cap covered only by luck.
#
# THE MEASURED NUMBER MOVES BETWEEN RUNS AND THAT IS EXPECTED. Gameplay RNG is unseeded, so the
# soak samples MarsBoss's entry curve wherever it happens to land: three runs of this exact rig
# read 1.777 / 2.013 / 2.404. The probe is still deterministic in its VERDICT because the shipped
# threshold sits a factor of two clear of that whole band -- which is the reason it sits there.
# Do not read any single [velscan] figure as exact, and do not tighten the threshold toward one.
#
# MUTATION-TESTED at 1.0 (below the whole band): the verdict line reads
# `[velscan] fastest non-repositioning=MarsBoss 2.013 px/ms, threshold=1.00 -- FAIL` and the
# `expect ... PASS` leg fails. NOTE a mutation to 2.0 -- INSIDE the band -- passed on one run and
# failed on the next, so a mutation test of this probe has to clear the variance too, or it proves
# nothing.

step 200 nodraw
eval NetVelScan true
step 30000 nodraw
eval NetVelScan false

# Positive control first: a run that sampled nothing prints VACUOUS rather than a low ceiling, and
# MarsBoss being in the table is what says the soak actually reached the boss fight.
expect \[velscan\] observed \|vel\| per replicable type
expect MarsBoss
expect \[velscan\] fastest non-repositioning=.* -- PASS
expect-not VACUOUS
expect-not -- FAIL
# COVERAGE (card e79bb994). The POSITIVE half first, and it is not optional: a build with every
# NetNoteTeleport call deleted prints no UNMARKED lines either -- it just stops announcing
# repositions -- so the absence assertion below means nothing without proof that marking happened
# at all. SpiderBoss is the card's own site and this level is where it lives.
expect SpiderBoss .* marked=[1-9]
# ...and the absence: no reposition in this whole soak went out unmarked.
expect-not UNMARKED teleport
quit
