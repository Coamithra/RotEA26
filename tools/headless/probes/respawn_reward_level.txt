# PROBE: the respawn reward bomb is sized by the player's OWN "2" powerup level, latched at the
#        moment the summon is raised (card ed32efe1).
#
# PINS:  three separate claims, and the file is built so each fails on its own.
#
#   1. THE LEVEL IS THE SLOT'S LINKER LEVEL, not a constant. The "2" is
#      `Powerup.PowerupType.Linker` (`Powerup.PowerUpString` renders it as "2"), which is already
#      the respawn powerup -- `PlayerShip.PowerUp` spends its level on `respawntimebonus`, i.e. on
#      this very clock. The pre-card build shipped a fixed 3 (card 258afd66, itself down from 4),
#      so `level=3` and `level=4` are the two values that separate the eras. This probe asks for
#      4 for that reason: it is neither the old constant nor the zero a broken read gives.
#
#   2. IT IS LATCHED AT SETUP, NOT READ AT THE POP -- which is not a stylistic choice, it is the
#      whole fix. The pop SPAWNS THE SHIP two lines before it builds the blast, `ComponentBin.Add`
#      runs `Initialize` synchronously, and `PlayerShip.Initialize` calls
#      `Score.ResetPowerup(player)`, which zeroes every level on that slot. A build that read the
#      score at the pop measured 0 for a maxed "2" on every single run (measured, before the
#      latch). The probe reproduces that wipe EXPLICITLY as well -- it drops the slot to 0 thirty
#      frames after the raise and asserts the drop took -- so the surviving 4 cannot be a slot that
#      simply never got reset.
#
#   3. THE VALUE REACHES Blast.Setup, witnessed INDEPENDENTLY of the print. `Blast.Setup` makes the
#      lifetime `1000ms * (level+1)` and `BombRipple` seeds its ring from that real lifetime (card
#      03c379f2), so `eval RippleState` reads `/5.00` at level 4 and `/1.00` at level 0. That
#      number comes off the Blast through the ripple, not off PlayerShipSummon at all.
#
# WHY THE SEAM (eval RespawnRaise): the summon's production trigger is a CO-OP death. A
# single-player death is a world WIPE and raises no summon at all (PlayerShipSummon.ShouldSummon),
# and the one level that seats a second local ship offline -- TeamChallenge -- is shared-fate, so
# GameScene.LoseLife purges the summon within ~10 frames of it being raised. `?harness=respawn&
# harnessrun` does run one, but raises it at BOOT, which is too early to be given a powerup level
# first -- and the ordering IS claim 2. `eval PowerupLevel` is the other half: no offline rig can
# otherwise put a level on a slot (no ship to pick a powerup up, no spawner roll to win).
# Both drive production code: the real `Setup` + `ComponentBin.Add`, and the wire's own
# `NetSetPowerupLevel`.
#
# FAILURE MEANS:
#   `reward=3` or `reward=0` at the raise -> the level is not being read off the "2" at all.
#   `reward=4` but `reward blast ... level=0`   -> the latch is gone; the read moved back to the
#                                                  pop and the ship spawn wiped it underneath.
#   the RippleState leg red with the others green -> the printed level and the one handed to
#                                                  Blast.Setup have drifted apart.
#   `[poweruplevel] slot=0 type=Linker level=0` missing after the raise -> the wipe leg is vacuous.
#
# COMPANION: respawn_reward_level_zero.txt runs the same rig at level 0 and requires `/1.00`, so
# neither file can pass on a build that returns a fixed maximum. Read the two as one probe.
#
# MUTATION-TESTED, three ways, each isolated. The runner stops at the first failed expect, so each
# mutation reddens one leg and the ones after it are not reached:
#   * the level back to a fixed 3 (the pre-card build): the RAISE leg goes red, `reward=3`. Both
#     files fail -- the constant is wrong for either asked-for level.
#   * the latch dropped (Score read at the pop again): the raise leg still reads `reward=4`, and
#     the POP leg goes red with `level=0` -- the ship spawn wiped the slot underneath it. This
#     file alone; the zero companion passes, because 0 is what a broken read gives anyway.
#   * the level floored at 1: this file passes and the ZERO COMPANION goes red (`level=1`), which
#     is the asymmetry the companion exists for. Do not read either file's green alone.
#
# eahl: --flags "?level=Level2&invuln&noattract&seed=1&difficulty=Medium"

# Settle into the level with a live ship in slot 0. Level 2 rather than Level 1 on purpose: Level
# 1's intro cinematic holds the player spawn for ~10 s, so the summon would report
# "draw suppressed (world wiped)" and the rig would be testing a shipless world.
# `?difficulty=Medium` is PINNED rather than inherited: the raise leg asserts `ms=10000`, and the
# countdown scales with difficulty (round((15 - bonus) * 0.66..0.9)). Without it a saved profile at
# Hard would fail this file as "wrong reward" when the difficulty is what moved -- probes README
# rule 5, a precondition folded into a subject assertion.
step 400 nodraw
mark

# Give slot 0 a maxed "2" and raise a real summon. `reward=` is the latch read straight back.
eval PowerupLevel 0 Linker 4
expect \[poweruplevel\] slot=0 type=Linker level=4
eval RespawnRaise 0 0
expect \[respawn\] raise slot=0 bonus=0 ms=10000 reward=4
expect-not \[respawn\] raise .* reward=(0|3)$

mark
# Now WIPE the slot, exactly as the respawn itself will in a moment. Asserted, not assumed: a
# surviving 4 means nothing if the reset never happened.
step 30
eval PowerupLevel 0 Linker 0
expect \[poweruplevel\] slot=0 type=Linker level=0

mark
# Run through the pop. The ship spawn inside it runs Score.ResetPowerup for real, so by the time
# the blast is built the slot has been zeroed twice over -- and the latched 4 must still be what
# is spent.
step 620 nodraw
expect \[respawn\] reward blast slot=0 level=4
expect-not \[respawn\] reward blast slot=0 level=(0|3)

mark
# The independent witness: the ring's resolved duration IS the Blast's own lifetime.
step 20
eval RippleState
expect e=[0-9.]+/5\.00
expect-not e=[0-9.]+/(1|4)\.00

quit
